# 导读 01：EInkAgent 代码结构与 P1 面试问答

> 读法：先看第 1 节的地图，再跟着第 2 节走一遍真实请求，然后对照第 3 节读 `agent.py`。
> 第 4 节的问答先自己答，再看答案。

## 1. 项目地图：五层，每层只依赖下一层

```
入口层   examples/*.py（命令行演示、评测）     eink_agent/api.py（HTTP 接口）
           │
Agent 层  eink_agent/agent.py ── 模型↔工具的循环、失败处理、降级
           │                └─ eink_agent/answer_guard.py（最终回答的规则校验）
           │
工具层   eink_agent/agent_tools.py ── 给模型看的工具说明书 + 白名单 + 参数校验
           │                   └─ eink_agent/requirements.py（搜索参数的 Pydantic 模型）
           │
查询层   device_repository.py ── 三个 SQL 查询函数：search / detail / compare
           │
数据层   database.py + schema.sql ── SQLite 连接与表结构
           ↑
         data_import.py ← data/*.csv（真实数据的唯一来源）
```

| 文件 | 一句话职责 | 不负责什么 |
| --- | --- | --- |
| `device_repository.py` | 把查询条件变成 SQL，返回字典列表 | 不知道模型存在 |
| `agent_tools.py` | 告诉模型"有哪些工具、参数长什么样"，并校验参数 | 不处理失败，失败直接抛异常 |
| `agent.py` | 和模型来回对话，把工具失败转成模型能看懂的错误 | 不写 SQL，不判断回答内容是否违规 |
| `answer_guard.py` | 检查最终回答有没有声称完成了未执行的动作 | 不调用模型 |

**为什么这样分层**：每一层都能单独测试。`device_repository` 用临时数据库测，
`agent.py` 用假的模型客户端（`Mock`）测，谁都不需要真实的网络。这就是 136 个测试能在 1 秒内离线跑完的原因。

## 2. 跟着一次真实请求走一遍

输入：`比较一下 Kindle Paperwhite 2026 和 Kobo Clara BW`（2026-10-10 冒烟测试，状态 ok）

```
第 1 轮  agent → 模型：[system 提示词, user 问题] + 3 个工具说明书
         模型 → agent：我要调用 search_devices({"keyword": "Kindle Paperwhite 2026"})
                       和 search_devices({"keyword": "Clara BW"})      ← 一轮可以调多个工具
         agent：逐个执行 → 得到 2 条、1 条结果 → 作为 role="tool" 的消息追加进对话

第 2 轮  agent → 模型：[之前所有消息 + 两条工具结果]
         模型 → agent：我要调用 compare_devices({"device_ids": [45, 15]})
         agent：执行 → 2 条结果 → 追加进对话

第 3 轮  agent → 模型：[所有消息]
         模型 → agent：不再调用工具，直接给出对比表格
         agent：answer_guard 检查通过 → 返回 AgentResult(status="ok")
```

**关键认识**：模型从来不直接碰数据库。它只能"提出请求"，执行权永远在 Python 手里。
这就是为什么白名单和参数校验有意义——模型提出的请求可能是错的。

**对话消息的四种角色**（OpenAI 兼容接口的协议，DeepSeek 也用这套）：

| role | 谁写的 | 内容 |
| --- | --- | --- |
| `system` | 我们 | 规则：能做什么、不能做什么 |
| `user` | 用户 | 问题 |
| `assistant` | 模型 | 回答，或者 `tool_calls`（要调用哪些工具） |
| `tool` | 我们 | 工具结果，必须带 `tool_call_id` 对应到模型的那次请求 |

模型本身没有记忆，**每一轮都要把完整历史重新发给它**，所以 `messages` 列表只增不减。

## 3. 读 `agent.py`（276 行）

建议按这个顺序读，而不是从头读到尾：

1. **`run_agent`（第 195 行起）——主循环，先读它。**
   - 第 220 行：最多循环 `max_rounds` 轮（默认 5）。
   - 第 223–228 行：最后一轮设 `tool_choice="none"`，逼模型用已有结果作答。
   - 第 237–258 行：**模型没调工具 = 它在给最终回答**。空回答 → 降级；
     有违规声明 → 第一次要求重写，第二次直接 `blocked`。
   - 第 263–271 行：模型调了工具 → 逐个执行；失败 +1，成功清零。
   - 第 273 行：连续失败达到 2 → 降级。第 276 行：轮数用完 → 降级。
   - 记住三种结局：`ok`（正常）/ `degraded`（没完成）/ `blocked`（回答违规）。

2. **`_run_tool_call`（第 157 行）——执行一次工具调用，永远不抛异常。**
   它返回两样东西：给我们自己看的 trace 记录，和给模型看的 tool 消息。
   成功和失败走同一个出口，只是内容不同。

3. **`_parse_arguments`（第 83 行）和 `_execute`（第 123 行）——把四种失败分类。**
   `_execute` 的三个 `except` 从具体到宽泛：先接未知工具，再接参数校验错误，
   最后用 `except Exception` 兜底。顺序不能反，否则宽泛的会先把具体的吃掉。

4. **`ToolCallError`（第 75 行）——自定义异常，只用来在函数之间传递"结构化错误"。**
   `payload` 就是最终发给模型的 `{"type", "message", ...}`。

5. **顶部常量（第 24–64 行）**——所有"魔法数字"和固定文案都在这里，
   面试被问"阈值为什么是 2"时，答案在第 22–23 行的注释里。

**`raise ... from error` 是什么**：保留原始异常作为"起因"，调试时能看到完整链条，
但我们只把 `payload` 发给模型，原始异常不会离开 Python。

## 4. P1 面试问答（先自己答，再看答案）

### Q1. 模型返回 `search_devices({"colour": true})`，系统发生了什么？

**答**：
1. `_run_tool_call` → `_parse_arguments`：JSON 合法、是对象，通过。
2. `_execute` → `execute_tool` → `DeviceRequirements.model_validate`：
   模型配置了 `extra="forbid"`，`colour` 不是已知字段 → 抛 `ValidationError`。
3. `_execute` 接住，转成 `ToolCallError("invalid_arguments", "colour: Extra inputs are not permitted", expected_arguments={...})`。
4. `_run_tool_call` 接住，trace 记 `status="error"`，tool 消息内容是 `{"error": {...}}`。
5. 连续失败计数变成 1，没到 2，进入下一轮。模型看到 `expected_arguments.allowed`
   里有 `is_color`，下一轮通常会改正。

**追问点**：`extra="forbid"` 是关键。如果允许多余字段，`colour` 会被悄悄忽略，
搜索变成"不限颜色"，用户拿到错误结果却没有任何报错——这比报错更糟。

### Q2. 为什么不把异常原文发给模型？

**答**：三个理由。
- **安全**：原文可能含文件路径、SQL 语句（测试 `test_tool_exception_is_not_leaked_to_model` 专门验证 `/secret/path` 不外泄）。
- **没用**：模型看不懂 Python 栈，它需要的是"哪个字段错了、允许哪些字段"。
- **注入面**：异常文本可能夹带外部输入，原样交给模型等于多开一个提示注入的口子。

### Q3. 连续失败上限为什么是 2？设成 1 或 5 会怎样？

**答**：设成 1 → 模型一次小失误就放弃，浪费了自我纠正的能力（Q1 里第二轮通常能改对）。
设成 5 → 模型卡住时要多等 3 轮，每轮 2–5 秒，用户等十几秒还是失败。
2 = 给一次纠正机会，第二次还错说明它没在收敛。**这是延迟与成功率的取舍，不是算出来的最优值**，
P2 的评测数据可以验证或推翻它。

### Q4. "空结果"为什么不算错误？

**答**：查 2000 元以内的 13 寸彩屏，返回 0 条是**正确答案**，不是故障。
算成错误会有两个后果：计数器把正常查询当失败，可能误触发降级；模型被告知"出错了"，
可能乱改参数重试，而不是如实告诉用户"没有符合条件的设备"。

### Q5. 为什么"我不能替您下单"不会被拦截？如果是"订单这块我处理不了，但已帮您下单了"呢？

**答**：`answer_guard` 先按句号、问号、分号、换行切句，句子里出现"不能/无法/没有…"
就当作拒绝句跳过。"我不能替您下单"含"不能" → 跳过。

第二句**会被拦截**：整句只用逗号连接，是一个句子；"处理不了"不在否定词列表里，
所以这句不算否定，"已帮您下单"命中。（已实测：返回 `['已帮您下单']`。）

**但换成"我无法处理退款，但已帮您下单了"就会漏判**：同一个句子里有"无法"，整句被跳过。
（已实测：返回 `[]`。）

### Q6. 拦截规则的局限？

**答**：两类漏判，均已实测确认：
- **否定词污染**：否定词和完成声明用逗号连在同一句里（见 Q5）。
- **换说法**："订单已经提交好了"不含任何关键词 → 返回 `[]`。

一类误判风险：否定词列表里的"未"太宽，比如"未公布价格，已为您下单"会被整句跳过（同属第一类）。

**为什么接受这些局限**：它是第一道防线，成本为零、结果确定、可测试。
漏判由 P2 的评测用例持续覆盖；当前系统没有任何下单工具，即使漏判，也不会真的下单——
最坏情况是回答里有一句假话。

### Q7. 为什么用规则判断，而不是再调一次模型当裁判？

**答**：
- **确定性**：同样的输入永远同样的结果，能写单元测试；模型裁判每次可能不同。
- **成本与延迟**：每个回答多一次模型调用，翻倍的钱和时间。
- **裁判也会错**：公开的 Agent 项目评测里，有裁判模型给"已为您更新地址"
  （系统根本没有改地址的工具）打满分的例子。

**加分回答**：两者不是二选一。规则适合"有明确特征、后果严重"的问题（声称下单）；
模型裁判适合"需要理解语义"的问题（回答是否切题）。P2 可以两者都用，但规则先行。
