# 009 会话记忆：结构化偏好 + 会话摘要（P5）

时间盒：最多 10 小时（AGENTS.md P5），自 2026-10-14 开始计。

## 问题

现在服务端不存任何东西：页面每次把最近 10 条消息发过来，Agent 只看得到这 10 条。
用户第一轮说"预算 2000、要手写"，聊了五六轮之后再问"推荐几款"，预算早已滑出窗口；刷新页面则全部丢失。
用户修正偏好（"预算改成 1500"）时，也没有任何地方记录"当前生效的是哪一个"。

## 参考与取舍（只借鉴机制，不复制代码）

参考项目用 Redis 存最近消息、ChromaDB 存摘要和用户画像，每轮额外调用一次模型提炼画像。
借鉴：分层、阈值写成常量、摘要失败时兜底。不照搬的原因：

- 画像是模型生成的自由文本，冲突时直接覆盖、没有历史；跨会话读取时不按时间排序，生效的是哪条不确定。
- 记忆读写没有捕获异常，存储故障会让对话接口返回 500。
- 画像只按用户 ID 精确查询，没有用到向量检索。

## 候选方案（偏好怎么写入）

**A：Agent 调用 `remember_preferences` 工具。** 字段固定、代码校验，调用出现在工具轨迹里，复用现有的错误处理与评测。
风险是模型忘记调用，用评测衡量。

**B：每轮结束后再调用一次模型提取偏好。** 不依赖主模型，但每轮多一次调用（成本、延迟、多一种失败）。

**选 A**（作者 2026-10-13 确认）。

## 设计

**三层：**

| 层 | 内容 | 常量 |
| --- | --- | --- |
| 工作记忆 | 最近的消息原文 | `MAX_HISTORY_MESSAGES = 10`（沿用现值） |
| 会话摘要 | 滑出窗口的旧消息压缩成一段话 | 滑出窗口且未摘要的消息达到 `SUMMARY_BATCH_MESSAGES = 6` 时触发；摘要上限 `MAX_SUMMARY_CHARS = 500` |
| 结构化偏好 | 预算上限、尺寸范围、重量上限、手写、彩色、开放系统、类别、品牌 | 字段与 `search_devices` 参数一致 |

摘要每次由"旧摘要 + 新滑出的消息"重新生成一段，而不是拼接，长度有上限。

**冲突更新规则：** 偏好按事件追加存储（`session_id, field, value, created_at`），从不修改旧行。
某字段的当前值 = 该字段最新的一行；值为 null 表示用户撤销了该偏好。可以按时间列出全部历史。

**偏好怎么用：** 当前偏好以中文描述放进一条单独的 system 消息，提示词要求搜索时应用、用户本轮明确改口时以本轮为准，
用户说出或修改长期偏好时调用 `remember_preferences`。
不在代码里把偏好强行合并进搜索参数：按名称查设备（"Kindle Scribe 多少钱"）时强加预算会把它过滤掉。

**会话标识：** `POST /agent` 增加可选 `session_id`（页面生成 UUID，存在浏览器里）。
- 不传：行为与现在完全相同，服务端不存任何东西。
- 传了：历史由服务端按会话读取（此时请求里的 `history` 必须为空，否则 422），回答后写入本轮消息；响应增加当前偏好。
- 新增 `GET /sessions/{session_id}`：返回消息、当前偏好与偏好历史，刷新页面后恢复对话。

**存储：** `eink_agent/memory.py` 中的 `SQLiteMemoryStore`，独立文件 `data/memory.db`（不入库，路径可用 `MEMORY_DB_PATH` 覆盖），
与设备库分开，重建设备库不会清掉用户记忆。存储对象通过参数传入 Agent 与 API，测试用临时文件。

**失败隔离：** 读记忆失败 → 当作没有记忆继续回答；写记忆失败 → 回答照常返回；摘要生成失败 → 保留旧摘要，下次再试。
`remember_preferences` 工具失败按现有规则作为结构化错误回传模型。

## 换成 Redis 时怎么映射（现在不做）

偏好当前值用 Hash，偏好历史用 Stream 或 List，消息用 List，摘要用 String，会话过期用 TTL。
值得换的条件：多实例部署共享会话，或需要自动过期。现在是单进程，SQLite 足够。

## 验证

- 离线测试：存储层（追加、取当前值、撤销、历史顺序）；三轮对话（设定 → 修正 → 第三轮的搜索参数用修正后的值）；
  存储故障时对话照常；摘要触发、失败兜底、长度上限；API 的 `session_id` 与 `history` 互斥、刷新恢复。
- 评测：新增记忆用例（需作者批准），比较"只有 10 条窗口"与"有记忆"两种情况下第三轮搜索参数是否应用了正确的偏好。

## 已知限制

- 拿到 `session_id` 就能读取该会话，适合本地演示，不适合多用户部署（没有登录）。
- 不做跨会话记忆：选购设备是一次性的任务，没有使用场景。
- 模型可能忘记调用 `remember_preferences`，或在用户只是随口一问时也记下偏好，由评测衡量。

## 补充：记忆评测（2026-10-14，作者批准 mem01–mem06 与 `forbidden_calls`）

- 用例带 `setup_turns`：前几轮用真实模型逐轮跑完，只评最后一轮。每条用例跑两遍：
  **有记忆**（每条用例一个临时存储，走与 `POST /agent` 相同的 `answer_in_session`，每轮后执行摘要步骤）与
  **只有窗口**（不给记忆，只回放最近 10 条消息）。有记忆的结果计入总通过数，只有窗口的结果单独列为对照。
- 新判定 `forbidden_calls`：最后一轮中，成功执行的调用若带有某个参数值（`arguments`）或某个参数（`argument_names`），
  即判失败（`forbidden_call`），即使之后又做了正确的调用，因为错误的搜索已经执行。
- 报告另给"前几轮调用了 `remember_preferences` 的用例数"，衡量模型是否记得写入。
- 批准时的通过条件只写了参数；按 P2 的规则（每条要求都要检查返回记录数，由 `test_case_file_is_well_formed` 强制），
  补上了记录数：mem01 2、mem02 0（预算 1500 内没有支持手写的设备）、mem03 20（26 台，工具最多返回 20）、
  mem04 5。mem06 接受两种情况：只带预算 3000（20 条），或保留手写偏好（9 条）。
- 预期：mem01、mem02、mem03、mem05、mem06 的设定都还在 10 条窗口内，两种情况都可能通过；
  mem04 的偏好在第 1 轮，最后一轮时已滑出窗口，是主要拉开差距的用例。对照结果如实报告，不为拉开差距改用例。
- 已知限制：模型裁判（decision 007）只看 `history` 与最后一轮，看不到 `setup_turns`，记忆用例的裁判结果不可靠。
