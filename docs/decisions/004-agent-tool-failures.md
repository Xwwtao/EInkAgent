# 004 Agent 工具失败处理与确定性回答校验（P1 最小版）

## 问题

`eink_agent/agent.py` 的主循环对工具调用没有任何保护：

- 模型返回非法 JSON 参数 → `json.loads` 抛异常，整个请求失败；
- 未知工具名、参数校验失败（Pydantic `ValidationError`）、工具内部异常 → 同样直接冒泡；
- 超过轮数上限 → 抛 `RuntimeError`，用户拿不到任何回答。

此外，模型可能在没有任何下单工具的情况下回答"已为您下单"，当前没有任何拦截。
接入 HTTP 接口和界面后，以上任何一种情况都会变成 500 错误。

## 候选方案

**方案 A：失败转成结构化工具消息回传给模型，并计数降级。**
模型看到"错误类型 + 原因 + 参数要求"，有机会在下一轮自行纠正。

**方案 B：任何工具失败都直接结束请求，返回固定的道歉文案。**
实现最简单，但模型的一次小失误（如多传一个字段）就会让整个请求作废。

## 选择：方案 A

参数错误是模型最常见的失误，且通常一次反馈就能纠正。直接放弃（方案 B）浪费了
已经完成的上下文。

## 行为定义

**错误分类**（写入工具消息和 trace 的 `error.type`）：

| 类型 | 触发条件 | 回传给模型的内容 |
| --- | --- | --- |
| `invalid_json` | 参数不是合法 JSON 对象 | 原因 + 该工具参数摘要 |
| `unknown_tool` | 工具名不在白名单 | 可用工具名列表 |
| `invalid_arguments` | Pydantic 校验失败 | 出错字段与原因 + 参数摘要 |
| `tool_error` | 工具执行时抛出异常 | 固定文案"工具执行失败"，**不含异常原文** |

空结果（返回 0 条）**不是错误**：正常回传 `[]`，`result_count = 0`，由模型如实告知。

**常量**（`eink_agent/agent.py`）：

- `MAX_CONSECUTIVE_TOOL_FAILURES = 2`：给模型一次纠正机会；连续第二次失败说明它没有收敛，
  继续重试只会增加延迟（每轮一次模型调用，约 2–5 秒）。任一成功调用将计数清零。
- `max_rounds` 默认值保持 3；超过上限不再抛异常，而是返回降级结果。

**降级结果**：`AgentResult.status = "degraded"`，`answer` 为固定文案，
说明没能完成查询并建议用户换个说法；trace 照常返回，便于排查。

**确定性回答校验**（新模块 `eink_agent/answer_guard.py`，不调用模型）：
当前没有任何会产生副作用的工具，因此答案中出现"已下单 / 已购买 / 已付款 /
已修改 / 已删除"等完成声明，一定是未执行的动作。命中时要求模型重写一次；
重写后仍命中，返回 `status = "blocked"` 和固定的"无法确认"文案。

**trace 结构**：失败调用也写入 `tool_trace`，新增 `status`（`ok` / `error`）与 `error` 字段。
评测按顺序比较调用，失败调用同样计入，口径不变。

**同时修正**：系统提示词与工具描述改为真实数据口径（价格是带采集日期的快照、
美元价按固定汇率换算、`NULL` 表示来源未公布、不得推断）；
`examples/tool_calling_agent_demo.py` 不再向真实数据库写入演示设备。

**不在本次范围**：模型 API 自身的错误（超时、429、5xx）仍向调用方抛出，
由下一步的 `POST /agent` 接口统一转换为 HTTP 错误码。

## 验证

`python -m pytest -q`。每类失败各一个测试；"轨迹为空但回答称已下单"必须被拦截；
连续两次失败返回 `degraded`；第一次失败、第二次成功的情况能正常返回答案。

## 背后的知识（面试准备）

1. **为什么不把 traceback 交给模型？** 三个原因：会泄露内部信息（文件路径、SQL）；
   模型无法根据栈帧修正参数，只会浪费 token；异常文本可能包含外部输入，
   相当于给提示注入开了一扇门。模型需要的是"哪个字段错了、应该是什么"。
2. **为什么计"连续"失败而不是"总"失败？** 失败后成功说明模型已经纠正，
   不该被之前的失误惩罚；连续失败才说明它卡住了。
3. **为什么用规则校验而不是让另一个模型来判断？** 规则是确定性的：同样的输入永远得到
   同样的结果，可以写单元测试，也不额外花钱。用模型当裁判本身也会出错——
   公开的 Agent 项目评测里有过裁判模型给"已为您更新地址"（系统根本没有改地址的工具）
   打满分的例子。
4. **为什么只重写一次？** 重写本身也是一次模型调用。一次重写能修正大部分偶发措辞问题；
   如果仍然违规，说明问题出在别处，继续重试只会增加延迟，不如明确告诉用户"无法确认"。
5. **规则校验的局限**：关键词匹配会漏掉换一种说法的声明（如"订单已提交"），
   也可能误伤否定句（"我无法为您下单"）。实现时需要排除否定句，漏判风险记录在案，
   由 P2 的评测用例持续覆盖。

## 补充（2026-10-11，P3 联调发现）

真实对话中模型把工具结果的字段名原样写进回答（如"封闭系统（is_open_system=0）"）。
`answer_guard.find_internal_field_names` 检测带下划线的已知字段名，命中时与"未执行动作声明"
共用同一次重写机会。两者的处理不同：

| 问题 | 重写后仍存在 | 理由 |
| --- | --- | --- |
| 声称已下单等 | `blocked`，返回固定文案 | 假话会误导用户 |
| 字段名外露 | 保留回答，`status = ok` | 事实正确，只是措辞生硬；拦截会丢掉有用信息 |

不检测 `brand`、`model` 等普通单词，避免误伤正常句子。系统提示词同时去掉了
`lowest_price_cny` 这个字段名，避免示范模型使用字段名。
