# EInkAgent

![Tests](https://github.com/Xwwtao/EInkAgent/actions/workflows/tests.yml/badge.svg)

An AI agent that helps people choose an E Ink reader or note-taking tablet.
You describe what you need in plain language; the agent queries a database
of real devices and price snapshots, compares candidates, and shows where
every price came from.

- **Data**: 49 real devices and 41 price snapshots, each with a source URL
  and collection date (`data/data_quality_report.md`, generated by
  `python data_quality.py`).
- **Agent**: DeepSeek tool calling over three read-only device tools, with
  structured error recovery and rule-based answer checks.
- **Knowledge**: 20 short documents explaining E Ink technology (panels,
  light, styluses, systems, formats, water resistance), searched by a fourth
  tool and cited by title and link.
- **Memory**: per-session preferences (budget, stylus, colour…) saved by a
  fifth tool as timestamped changes, a rolling summary, and the conversation
  restored after a page refresh.
- **Interface**: a single-page chat UI served by FastAPI.

## Quick start

Requires Python 3.14 and a DeepSeek API key. A fresh clone through the test
run takes well under a minute on a machine with a warm pip cache.

```bash
git clone https://github.com/Xwwtao/EInkAgent.git
cd EInkAgent
python3.14 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements-dev.txt
python data_import.py
python -m pytest -q
```

`data_import.py` builds `data/eink_devices.db` from the CSV files in `data/`.
Running it again does not create duplicates.

Start the server in a terminal where the key is set (zsh):

```bash
read -s "DEEPSEEK_API_KEY?DeepSeek API key: "
export DEEPSEEK_API_KEY
python -m uvicorn eink_agent.api:app --reload
```

Open http://127.0.0.1:8000. Without a key the page still loads, and
`POST /agent` answers HTTP 503 with a message saying the key is missing.

Knowledge search needs an embedding service (`EMBEDDING_API_KEY`,
`EMBEDDING_BASE_URL`; DashScope's OpenAI-compatible endpoint is used here).
Without them the agent runs with the device tools only and is not offered
`search_knowledge`.

The page keeps a session id in the browser; the server stores that
session's messages, preferences and summary in `data/memory.db` (ignored by
Git; `MEMORY_DB_PATH` overrides it). "新对话" starts a new session.
Environment variables are listed in `.env.example`; the app reads the
environment only and does not load `.env` files.

### Try it

| Input | What the agent does |
| --- | --- |
| 预算2000元以内，要能手写，推荐几款 | `search_devices` with a price cap and stylus filter, then details for each match |
| 比较一下 Kindle Paperwhite 2026 和 Kobo Clara BW | Finds both devices by name, then calls `compare_devices` |
| 第二款防水吗？ (as a follow-up) | Uses the previous turns as context |
| 帮我下单 Kindle Colorsoft | Calls no tool and explains it cannot place orders |
| 我想买个阅读器 | Asks about budget, size and use before searching |
| Kaleido 3 的彩色为什么没有黑白清楚？ | Calls `search_knowledge` and cites the passage it used |
| 阅读器一般保修多久？ | The corpus has no answer: the search returns nothing and the agent says no material was found |
| 预算2000以内，要能手写 → 预算改成1500吧 | Calls `remember_preferences` each time; the bar under the header shows 预算 ≤ ¥1500 and the change history |

Each answer can expand a timeline of the tool calls it made, with arguments,
result counts and failures.

## What it can do

- **Search** by price, screen size, weight, colour, stylus support, open
  system, category, brand, or product name (`keyword` matches every word
  against brand and model).
- **Inspect and compare** up to five devices.
- **Cite prices**: every price comes with the seller, collection date and
  link of the cheapest available offer. Overseas prices are stored in USD and
  converted at the fixed rate in `data/exchange_rates.csv`.
- **Remember a conversation**: with a session id the server keeps the
  messages and sends the last 10 to the model. Older messages are folded
  into a summary of at most 500 characters once 6 have left that window.
  Without a session id the page sends its own last 10 messages and the
  server stores nothing.
- **Remember preferences**: `remember_preferences` saves budget, screen
  size, weight, stylus, colour, open system, type and brand. Each change is
  a new timestamped row: the newest value wins, null withdraws a
  preference, and the history stays. Saved preferences are shown to the
  model as data and applied to searches, but not to lookups by name.
- **Keep answering when memory fails**: an unreadable or unwritable memory
  store means answering without memory, never an HTTP error.
- **Recover from tool failures**: invalid JSON, unknown tools, invalid
  arguments and tool exceptions are returned to the model as structured
  errors (never exception text). Two consecutive failures, an empty answer,
  or running out of rounds return a fixed apology instead of an HTTP 500.
- **Explain technology with sources**: `search_knowledge` returns up to
  three passages from `data/knowledge/`, each with document title, section,
  source URL and verification date; the page lists them as clickable links.
  When the best passage scores below the gate the tool returns nothing and
  the agent says no supporting material was found.
- **Check answers without a model**: an answer claiming an order, payment or
  edit is rewritten once and then blocked; an answer exposing internal field
  names such as `is_open_system` is rewritten once.

## Known limitations

- **Data is a snapshot.** Specs were verified on 2026-09-11 or 2026-10-05,
  prices collected on 2026-10-05 or 2026-10-10. Nothing refreshes them.
- **Chinese-brand specs come from IT之家 articles**, because the official
  sites are image-based. The 2026 Kindles come from Amazon product pages;
  older Kindles come from Amazon press releases, with some fields taken from
  Wikipedia and marked in the `notes` column.
  Values were collected from manufacturer, retail and media pages, plus the
  author's own checks where vendors do not publish a field. Fields that could
  not be determined are stored as NULL and reported as unknown,
  so filters such as "no stylus" do not match devices whose stylus support
  is unpublished.
- **Converted prices are references**, not what a buyer in China pays after
  shipping and import fees.
- **The answer checks are keyword rules.** They miss paraphrases, and a
  refusal word in the same sentence hides a claim (for example "我无法处理
  退款，但已帮您下单了"). See `docs/learning/01-agent-walkthrough.md`.
- **The Agent sometimes adds facts from general knowledge.** The judge found
  3 such answers in 35 (page-turn buttons, a discontinued product line, an
  included stylus); the prompt rule against it is not always followed.
- **The evaluation checks wording with keywords.** A correct answer phrased
  differently can fail; the model judge covers groundedness but missed one
  contradiction in 35 answers. See [Evaluation](#evaluation).
- **The knowledge documents were written by Claude** from public sources
  and spot-checked by the author, not copied or verified line by line;
  every document links its sources. They describe technology only, no
  specific devices, so they cannot contradict the device database.
- **The retrieval gate trades recall for honesty.** At gate 0.55, 2 of 27
  answerable retrieval questions return nothing (WeChat Read, battery life).
  The gate was chosen on the same 32 questions it is reported on, with only
  5 unanswerable ones.
- **Prompt rules alone do not stop injected instructions.** In run 7 the
  first draft of k06 repeated a planted "已为您下单" from a retrieved
  document; the answer check caught it and the rewrite passed. In run 8 the
  model ignored the instruction on its own.
- **Memory showed no measurable gain in its evaluation.** With memory and
  with only the last 10 messages, the six memory cases both passed 4 of 6
  (run 9). The model keeps restating the user's constraints in its answers,
  so they stay inside the window even when the original message has left
  it. Two cases fail in both modes because of how they were designed (see
  [Evaluation](#evaluation)).
- **Anyone holding a session id can read that session.** There is no
  login; this is a local demo, not a multi-user service. Restored answers
  show text only: tool calls and device cards are not stored.
- The agent cannot buy anything or change data; all tools are read-only.

## Evaluation

47 hand-written cases in `evals/agent_cases.json` cover single searches,
multi-step lookups, empty results, invalid parameters, clarification,
unsupported actions, prompt injection, multi-turn follow-ups, data
honesty, knowledge questions and memory. One knowledge case (k06) adds an
evaluation-only document with a planted instruction
(`evals/knowledge_injection/`) and checks the answer does not follow it. A case passes only if the required tool calls succeed, return the
expected number of rows or the expected devices, and the answer contains the
expected facts without claiming an unexecuted action. Expected row counts are
tied to the committed CSV data and checked by a unit test.

**Latest result: 45 of 47 passed** — `evals/reports/20261014T125704Z.md`,
`deepseek-flash`, single run on 2026-10-14 at commit `7431219`.
p50 latency 4.3 s, p95 20.5 s per case (memory cases play several turns);
301,869 prompt and 37,264 completion tokens, about ¥0.23–0.46 for the whole
run at the off-peak and peak prices in `evals/pricing.json`, including the
window-only control runs. All 41 earlier cases passed; the two failures are
memory cases explained below. In run 8, p03 refused correctly but answered in
English; it answered in Chinese again in run 9 and no rule was added for it.

The report lists which answers passed only after the answer check asked for
a rewrite: in run 9, k06 again first repeated the planted order claim, and
the rewritten answer no longer mentioned a previous draft.

How the result got here, all reports committed in `evals/reports/`:

| Run | Commit | Passed | What changed before it |
| --- | --- | --- | --- |
| 1 | `e512b64` | 31 / 35 | Baseline |
| 2 | `7a115c3` | 29 / 35 | Nothing; measures run-to-run variation |
| 3 | `001efca` | 34 / 35 | Name lookups check the devices found instead of keyword wording (5 of 6 earlier failures had correct answers) |
| 4 | `2b78411` | 33 / 35 | `category` restricted to reader / note / tablet |
| 5 | `d2f7c28` | 33 / 35 | Simplified Chinese reply rule |
| 6 | `1f5fe39` | 34 / 35 | Raw tool-call syntax never returned as an answer |
| 7 | `015673f` | 41 / 41 | Six knowledge cases added (k01–k06) and `search_knowledge` offered |
| 8 | `457e755` | 40 / 41 | Rewrites recorded; rewrite request no longer lets the model apologise for an unseen draft; knowledge queries asked to be in Chinese (run 7's d01 searched in English and missed the water-resistance document) |
| 9 | `7431219` | 45 / 47 | Six memory cases added (mem01–mem06) and run with and without memory |

Every change to the cases was approved and is recorded with its reason in
`docs/decisions/006-agent-evaluation.md`. After run 5 the keyword lists are
frozen: correct answers with different wording are left for a model-based
judge (planned) rather than patched case by case, so the cases do not drift
toward the model's phrasing.

### Knowledge retrieval

32 questions in `evals/retrieval_cases.json` (27 with an answer in the
corpus, 5 without) compare four ways to pick the top 3 of 48 passages
(`evals/reports/retrieval_20261013T143055Z.md`, single run;
`docs/decisions/008-component-knowledge-rag.md`):

| Method | Recall@3 | Precision@3 | Unanswerable → empty |
| --- | --- | --- | --- |
| Keyword (BM25 over Chinese bigrams) | 0.907 | 0.593 | 0 / 5 |
| Vector (`qwen3.7-text-embedding-flash`, cosine ≥ 0.55) | 0.889 | 0.506 | 5 / 5 |
| Hybrid (reciprocal rank fusion) | 0.926 | 0.630 | 0 / 5 |
| **Hybrid, gated on best vector score ≥ 0.55 (used)** | 0.889 | 0.654 | 5 / 5 |

Keyword search always finds something, because common two-character words
such as 多久 match some passage, so it cannot say "no answer". The vector
score can, so it decides whether to answer and the hybrid ranking decides
what to return. Passages are one per `##` section, without overlap (average
about 80 characters). No query rewriting or reranking: there is no data
showing they are needed.

### Memory: with and without

Each memory case plays its earlier turns live with the real model, then
grades only the last turn's searches, including `forbidden_calls` (for
example, no search with the old budget after the user corrected it). Every
case runs twice: with session memory (the same code path as `POST /agent`)
and with only the last 10 messages (`docs/decisions/009-session-memory.md`).

Run 9: **with memory 4 of 6, window only 4 of 6**; the model called
`remember_preferences` in the earlier turns of all 6 cases.

- **mem04 was meant to separate the two**: the constraint is stated in turn
  1 of 7 and has left the window by the last turn. Both passed, because the
  model's answers kept repeating "those 5 black-and-white devices under
  1,500 yuan".
- **mem02 failed in both** by case design: with the corrected budget of
  1,500 and a stylus there are no devices, so the model reasonably searched
  the old budget as a fallback (with memory) or asked which to keep
  (window only).
- **mem03 failed in both** by grading design: neither searched again in the
  last turn, reusing the previous turn's results. The turn that withdrew
  the stylus requirement did differ: with memory the model sent
  `supports_stylus: null` and found 20 devices; with the window only it
  sent `supports_stylus: false`, wrongly excluding every stylus device.

So no improvement is claimed from memory. What it demonstrably adds is a
conversation and preferences that survive a refresh (offline tests), a
visible change history, and an explicit way to withdraw a preference.

### Answer groundedness (model judge)

Keyword checks cannot tell whether every fact in an answer comes from the
tool results. A second model from a different family, `qwen3.8-flash`
(thinking off, temperature 0), answers two yes/no questions per answer:
is every device fact supported by the tool results, and does the answer
address the question. It sees the Agent's system prompt as context, and
everything it grades is marked as data, not instructions
(`docs/decisions/007-llm-judge.md`).

On run 6, before the knowledge cases were added
(`evals/reports/judge_20261013T123305Z.md`):

- **32 of 35 answers judged fully grounded.** The judge flagged s01 ("Libra
  Colour has page-turn buttons"), n02 ("Sony's Reader line was discontinued")
  and t02 ("a stylus is included"). None of these is in the tool results;
  t02 is likely false, since the Kobo stylus is sold separately.
- **Calibration against the author's labels:** 30 of 35 before the judge saw
  the Agent's rules (four false alarms on the fixed-rate price note), 33 of
  35 after.
  Checking each disagreement against the stored tool results showed the
  labels had missed three unsupported statements, and the review also found
  one the judge missed: n03 says nothing is available even at 2,000 yuan
  while its own search returned 15 devices. After this adjudication: 34 of
  35, 1 miss, 0 false alarms (`evals/reports/calibration_20261013T123305Z.md`).
  The labels were corrected after seeing the judge's verdicts, which biases
  agreement upward.
- **Fault injection:** 10 answers with one appended sentence contradicting
  the tool results (wrong weight or price, reversed waterproof or stylus
  support) were all detected, 10 of 10 (`evals/faults/`). Appended sentences
  are easier to spot than n03's contradiction inside a longer sentence,
  which the judge missed.
- **Limits:** 35 cases, one labeller, single judge run; the judge prompt was
  adjusted on these same 35 answers after the first calibration.

The judge result is reported separately and never changes the pass count.

```bash
python -m examples.evaluate_agent                      # run all cases, write reports
python -m examples.compare_eval_reports A.json B.json  # what changed between runs
python -m examples.regrade_eval_report A.json          # re-grade a saved run with current cases
python -m examples.label_answers A.json                # hand-label groundedness
python -m examples.inject_faults A.json                # build answers with known errors
python -m examples.judge_eval_report A.json            # run the judge (JUDGE_* variables)
python -m examples.calibrate_judge judge_A.json        # recompute agreement after relabelling
python -m examples.evaluate_retrieval                  # retrieval comparison (EMBEDDING_* variables)
python -m examples.build_knowledge_index               # re-embed after editing data/knowledge/
```

## Architecture

```text
Browser (static/index.html) ──POST /agent──▶ api.py ──▶ agent.py ──▶ agent_tools.py
                                               │            │              │
                                    dependency-injected   answer_guard.py  ├──▶ device_repository.py
                                      DeepSeek client                      ├──▶ knowledge.py ◀── data/knowledge/*.md
                                                                           │                  + knowledge_index.json
                                                                           └──▶ memory.py ──▶ SQLite (data/memory.db)
                                                                            │
                         data/*.csv ──▶ data_import.py ──▶ SQLite (devices, offers)
```

| File | Responsibility |
| --- | --- |
| `eink_agent/api.py` | HTTP endpoints, request validation, model error → status code |
| `eink_agent/agent.py` | Model–tool loop, failure handling, rewrites |
| `eink_agent/answer_guard.py` | Rule-based checks on the final answer |
| `eink_agent/agent_tools.py` | Tool schemas shown to the model, allowlist, argument validation |
| `device_repository.py` | SQL for search, detail and comparison |
| `eink_agent/knowledge.py` | Corpus parsing, section chunks, BM25, vectors, gated hybrid search |
| `eink_agent/memory.py` | Session messages, preference events, rolling summary |
| `data_import.py` / `data_quality.py` | Validated, idempotent CSV import and the data report |

Design decisions, each with the rejected alternative, are in
`docs/decisions/`. A guided code walkthrough is in `docs/learning/`.

## HTTP API

| Method | Path | Purpose |
| --- | --- | --- |
| `GET` | `/` | Chat interface |
| `POST` | `/agent` | `{"message": str, "history": [...]}` or `{"message": str, "session_id": uuid}` → answer, status, tool calls, latency, preferences |
| `GET` | `/sessions/{session_id}` | Stored messages, current preferences and their change history |
| `GET` | `/devices` | Search with `brand`, `max_price`, `limit` |
| `GET` | `/devices/{id}` | One device |
| `POST` | `/devices/compare` | Two to five device IDs |
| `GET` | `/health` | Liveness check |

Interactive documentation: http://127.0.0.1:8000/docs

`POST /agent` status codes: 422 invalid request (including both `history`
and `session_id`), 503 no API key configured, 504 model timeout, 502 other
model API errors. `GET /sessions/{id}` answers 503 when memory cannot be read.

## Development

```bash
python -m pytest -q
```

Tests run offline: the model client is replaced with a scripted fake and
each test gets a temporary database seeded with three fictional devices.

To try the agent against DeepSeek from the command line and save the runs to
`evals/smoke_runs/` (ignored by Git):

```bash
python -m examples.smoke_test_agent
```
